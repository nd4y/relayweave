# Локальная маршрутизация и опциональные вычисления v1

[English](compute-v1.md) | **Русский**

Эта ветка реализует базовый уровень local-v1 и первый ограниченный протокол вычислений из спецификации маршрутизации 2.0. Это кандидат для разработки. Он не был развёрнут. Для производственной приёмки требуются доказательства, перечисленные ниже.

## Значения по умолчанию и границы

Развёртывание без изменений использует существующий алгоритм маршрутизации. Задайте `RELAYWEAVE_ROUTING_ALGORITHM=local-v1` на data-plane worker, чтобы включить локальный оценщик и кешированный селектор. Ручные, fallback-, sticky- и timed-политики сохраняют свои существующие пути кода. TCP и UDP имеют отдельные планы. GPU, обработка медиа, изменения интерфейсов/файрвола, новые пробы и изменения приоритета процесса Tdarr не выполняются.

Селектор использует только уже допущенные маршруты и текущие фильтры разрешений/работоспособности/egress. Конфигурация, отзыв, security lease и финальная проверка `RouteAllowed` сохраняют полномочия. Потеря вычислений не может продлить security lease. Истечение срока рекомендации не влияет на существующие потоки.

Локальная подготовка выполняется раз в секунду при наличии активных потоков и раз в десять секунд в режиме простоя. Она группирует псевдонимы endpoint, суммирует их активные сессии, берёт максимальную наблюдаемую скорость и использует наименее дорогой работоспособный представитель. Доставленная скорость является наблюдением, а не оценкой ёмкости. Недоступное активное измерение остаётся неизвестным. Дополнительная история и обёртки на основе байтов не устанавливаются.

## Начальная загрузка для разработки

Соберите `cmd/compute-admin`, `cmd/compute-worker` и существующую control plane на сборочном хосте. Используйте выделенного сервисного пользователя и новый каталог для идентичности вычислений. Команда начальной загрузки отказывается работать с существующим непустым каталогом.

```sh
compute-admin -action bootstrap -identity-dir /var/lib/relayweave-compute/authority
# Supply COMPUTE_DATABASE_URL through the existing protected service environment.
compute-admin -action provision -identity-dir /var/lib/relayweave-compute/authority \
  -installation installation-1 -worker-id compute-1 -peer-dir /secure/staging/compute-1
```

Передавайте только каталог peer через существующий защищённый канал администрирования. Он содержит `client.json` и `ca.pem`. Команда провижининга предназначена для администрирования Linux. В Linux сервисный пользователь worker должен владеть каталогом peer и его приватным набором с правами 0600; в Windows устанавливайте каталог peer с ACL, ограниченным его сервисной учётной записью и системными администраторами. Никогда не передавайте на compute worker файлы центра полномочий `ca.key`, `signing.seed` или `token.key`. Провижининг явно закрепляет открытый ключ клиента в allowlist. Второй сертификат с тем же именем и другим ключом не может выдать себя за него.

Задайте `RELAYWEAVE_COMPUTE_CONFIG` на control plane для разработки как защищённый JSON-файл:

```json
{"version":1,"enabled":true,"installation":"installation-1","listen":"127.0.0.1:9911","identity_dir":"/var/lib/relayweave-compute/authority","signing_seed_file":"/var/lib/relayweave-compute/authority/signing.seed","token_key_file":"/var/lib/relayweave-compute/authority/token.key"}
```

Для удалённого worker используйте явный частный/VPN-адрес. Wildcards, публичные адреса и неявные привязки по имени хоста отклоняются. Данная функция не устанавливает конфигурацию файрвола/VPN. Отсутствие этой переменной не создаёт слушатель вычислений, миграцию или цикл вычислений.

На data-plane worker установите `recommendation-keys.json` через доверенный канал администрирования, затем явно настройте:

```sh
RELAYWEAVE_ROUTING_ALGORITHM=local-v1
RELAYWEAVE_COMPUTE_INSTALLATION=installation-1
RELAYWEAVE_COMPUTE_KEYS=/etc/relayweave/recommendation-keys.json
RELAYWEAVE_COMPUTE_MODE=shadow
```

`shadow` проверяет рекомендации, но не маршрутизирует с их помощью трафик. Режим разработки `canary` использует когорту 1% со смешиванием рекомендаций 0.10; его нельзя включать в производстве до выполнения указанных условий приёмки. Offload требует как минимум двух групп с достаточными исходами и свежими активными измерениями. Он сохраняет доли ISP, поскольку в этой реализации нет независимого измерения ёмкости ISP. Неизвестный спрос не создаёт утверждения о ёмкости.

Для 0 worker используйте только local-v1. Для 1 worker запустите один ограниченный исходящий клиент с `examples/compute/compose.yaml`. Для 2 добавьте `-f examples/compute/compose.two.yaml` после базового compose-файла и провижиньте вторую идентичность отдельно. Близкий worker использует тот же протокол, что и удалённый worker. Глобальный бюджет является общим, а не удваивается для каждой политики или worker.

## Протокол и персистентность

Мажорная версия протокола - 1, цель - `objective-v1`. Go-структуры в `internal/compute/protocol.go` и `plan.go` являются авторитетным контрактом передачи. Сообщения используют ограниченный ASCII-канонический JSON только с целыми числами; дублирующиеся/неизвестные ключи, чрезмерная глубина/размерность, небезопасные целые числа и сжатие отклоняются. Дайджесты SHA256 и подписи Ed25519 связывают установку, исполнителя, идентификаторы HMAC-политики/группы, загрузку исполнителя, последовательность снимка, поколение конфигурации, эпоху владельца и диапазон кандидатов. Worker не получают подписок, адресов endpoint/назначения, учётных данных или команд.

`POST /compute/v1/register`, `/heartbeat`, `/lease`, `/result`, `/cancelled`, `/renew` требуют выделенных идентичностей TLS 1.3 mTLS. Клиент выполняет только исходящие запросы, отклоняет перенаправления и не принимает небезопасную проверку сертификатов. Токен полномочий результата передаётся только в заголовке Authorization. Токены полномочий генерируются стандартным PRF HMAC-SHA256 из защищённого ключа и уникальных идентификаторов попытки/сессии/задачи; сохраняются только их хеши. Это позволяет получить идемпотентный ответ на lease без хранения токенов полномочий в открытом виде.

`internal/compute/schema_v1.sql` - аддитивная, опциональная миграция, ограниченная таблицами вычислений. Владение использует время PostgreSQL, lease 10 секунд, продление 3 секунды и epoch fence. Извлечение из очереди и резервирование бюджета фиксируются вместе. Завершённые строки результатов образуют долговечный outbox публикации. Публикация независимо проверяет и подписывает под блокировкой строки текущей установки перед фиксацией; неудачная транзакция никогда не публикует конверт. Локальный исполнитель повторно проверяет подпись и кандидата. Результат пригоден не более 30 секунд с момента локального захвата с использованием Linux CLOCK_BOOTTIME или Windows GetTickCount64. Удалённые часы реального времени не могут его обновить.

Каждый дочерний процесс имеет резервирование CPU 500 мс, кооперативную отмену на 350 мс и крайний срок по настенным часам не позднее эпохи задачи. Ограничения дерева процессов - 1 CPU/512 MiB при одном дочернем процессе. Глобальный реестр ограничивает скользящие резервирования на уровне 1 CPU-секунды/10 секунд, 3 CPU-часов/UTC-сутки и 64 MiB/сутки байтов HTTP приложения. Неизвестные исходы тратят полное резервирование и держат свой слот в карантине в течение консервативных 62 секунд после истечения. Это зарезервированные байты приложения; они не являются измеренным лимитом сетевых байтов. Linux требует ограничений cgroup v2; при неподдерживаемой схеме выполнение запрещается. Windows использует отдельный [Job Object с жёстким ограничением CPU](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information). Нативные тесты проверяют ограничения ядра, наследование, реальный оценщик и kill-on-close; длительный стресс-тест границ CPU/памяти остаётся условием приёмки.

## Остановка, отзыв, продление и восстановление

- Создайте локально `<RELAYWEAVE_COMPUTE_KEYS>.disabled`, чтобы очистить рекомендации и остановить экспорт на следующем тике в одну секунду, не дожидаясь базы данных. Удаляйте маркер только после исправления. Удалите настройки окружения вычислений при следующем контролируемом перезапуске для постоянного отключённого состояния.
- Отзовите worker командой `compute-admin -action revoke -identity-dir ... -installation ... -worker-id ...`. Allowlist проверяется при каждом HTTP-запросе, включая запросы по существующим TLS-соединениям. Три недействительных результата за десять минут отзывают этого worker до явного повторного провижининга оператором. Некорректный/дублирующийся/неизвестный JSON, недопустимые значения результатов, отсутствующие токены полномочий, слишком большие тела и запрещённое сжатие учитываются после одобрения идентичности. Частичные загрузки и устаревшие попытки не учитываются. Счётчик и аудит фиксируются вместе; сбой учёта возвращает 503. Отключение после полностью недействительной загрузки не отменяет её ограниченную операцию учёта.
- Листовые сертификаты действуют семь дней. Worker продлевает тот же ключ, когда остаётся не более 48 часов; диспетчер продлевает свой лист локально. Продление не может изменить закреплённый открытый ключ. Продление в Windows использует [ReplaceFileW для сохранения существующего ACL файла](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files). Нативные тесты проверяют продление mTLS, неизменный приватный ключ и защищённый DACL; устойчивость к сбоям/потере питания остаётся условием приёмки. Перевыпускайте истёкшие учётные данные через канал администрирования.
- Изменения открытых ключей рекомендаций загружаются каждые пять секунд. Установка изменённого доверенного набора ключей очищает кешированные планы. Автоматического доверия к открытому ключу, переносимому в рекомендации, нет. Выполняйте перекрывающееся распространение ключей и подтверждение исполнителем через существующий доверенный операционный процесс перед подписанием новым ключом.
- Перед запуском вычислений после восстановления или потери их журнала базы данных выполните `compute-admin -action uncertain -identity-dir ... -installation ...`. Это отгораживает владельца и отключает вычисления на полные новые UTC-сутки. Локальный алгоритм остаётся доступным. Восстановление всех постоянных полномочий невозможно надёжно обнаружить из той же восстановленной базы данных; этот шаг является обязательной процедурой восстановления.
- Откат бинарника: остановите только сервис/контейнер вычислений, замените его ранее проверенной сборкой, затем зарегистрируйте новую сессию. Для отката вычислений не требуется перезапуск Tdarr или data-plane. Восстановите устаревшую маршрутизацию отдельно, удалив опцию local-v1 во время обычной процедуры обновления worker.

## Проверка и ограничения выпуска

Все сборки и тесты Linux выполняются на build-01 под общей блокировкой сборки проекта с ограниченными ресурсами контейнеров. Репозиторий содержит функциональные/race-тесты, fuzz-семена парсера, независимо сгенерированный вектор canonical/candidate/Ed25519 в `internal/compute/testdata`, интеграционные тесты PG и тесты области/отзыва mTLS. Тесты PG требуют `RW_COMPUTE_TEST_DATABASE_URL`, указывающий на одноразовую фикстуру; они создают и удаляют уникальные схемы. Тесты дочернего процесса/реального CLI требуют `RW_COMPUTE_WORKER_BINARY`. Нативные тесты только для Windows кросс-собираются на build-01 и запускаются как короткие отдельные процессы Windows с `RW_WINDOWS_NATIVE_GATE=1`; только их помощник присоединяется к собственному ограниченному Job Object. Синтетические идентичности и изменения ACL остаются внутри тестового каталога. Начальная загрузка административного CA остаётся только для Linux. Эти тесты проверяют поведение загрузочных часов/крайних сроков, но не моделируют физическое приостановление/возобновление хоста. `RW_RESOURCE_GATE=1` запускает парное 20-минутное сравнение селекторов (по 10 минут на каждое плечо) при 1000 попытках выбора/с с 256 маршрутами каталога и 16 подготовленными маршрутами, включая p99. `RW_RESOURCE_IDLE_GATE=1` измеряет десять минут абсолютного простоя CPU как консервативную верхнюю границу его приращения. Они выполняются без инструментирования race. Они не моделируют реальный трафик сокетов. Неудачное более раннее абсолютное измерение CPU сохраняется вместе с его хешем источника; оно не является успешной ресурсной проверкой.

Не делайте вывод о полной приёмке спецификации на основании модульных тестов. Оставшиеся доказательства для выпуска включают ресурсные проверки простоя/нагрузки/p99 на финальном исходном коде, стресс-тесты возобновления/часов и супервизора на обеих целевых ОС, фактическую нерегрессию сокетов/foreground/Tdarr, сетевой/проводной учёт, полную матрицу отказов и 24-часовую кампанию shadow. Производственное развёртывание требует явной авторизации оператора и завершения применимых условий приёмки. Авторизация на развёртывание не отменяет требования приёмки для включения local-v1 или вычислений.

Текущие отличия от полного дизайна 2.0 должны оставаться видимыми: числовые поля снимка охватывают только цель по задержке/надёжности и свежую активную скорость, неизвестные значения в этой версии используют нулевые сентинелы; не поставляются оптимизатор ёмкости ISP, офлайн-пакетный допуск, контекстное обучение, работа на GPU, новый допуск исследования пользовательских потоков, эксперимент по производственному качеству или автоматический поэтапный выпуск. Текущий конечный поиск намеренно мал: если измеренная стоимость локального поиска не превышает 10 мс и он находит тот же ответ, сохраните local-only или используйте удалённые worker для офлайн-валидации. Только удалённая доступность не является доказательством полезного offload.
