# Пути «прокси + ISP»

[English](dualwan.md) | **Русский**

RelayWeave может компилировать каждый допустимый профиль прокси в независимо проверяемые пути `(profile, egress)`. Включите это в «Настройки / Каналы ISP», затем спланируйте и примените конфигурацию. Существующие установки без `egress_paths` сохраняют прежнюю маршрутизацию. Интерфейс не меняет роутер, адрес хоста или WAN-интерфейс.

```json
"egress_paths": [
  {"id":"isp1","name":"Primary","source_ip":"192.0.2.11","enabled":false,"weight":8,"download_mbps":760,"upload_mbps":760},
  {"id":"isp2","name":"Secondary","source_ip":"192.0.2.12","enabled":true,"weight":5,"download_mbps":475,"upload_mbps":475}
]
```

Исходные адреса в примере предназначены для документации. Замените их зарезервированными адресами, действительно назначенными в сетевом пространстве имён воркера. Хотя бы один настроенный путь должен быть включён. Поддерживаются до четырёх путей и 10 000 скомпилированных маршрутов. Сбалансированным политикам нужны активные слоты для всех включённых ISP; действуют существующие пределы 16 горячих путей / 32 процесса. Отдельный воркер на ISP не нужен. Настройки глобальны и пока предполагают один воркер либо одинаковую локальную адресацию выхода во всех сетевых пространствах воркеров.

## Что делает sendThrough

`sendThrough` - настройка исходного IP исходящего соединения Xray, а не интерфейс, шлюз, идентификатор провайдера или протокол объединения каналов. Обычный системный dialer привязывает TCP- или UDP-сокет к этому адресу. Адрес должен принадлежать пространству имён воркера и соответствовать семейству удалённого адреса. Сам по себе выбор источника не гарантирует физический ISP. DNS-разрешение имён прокси может использовать системный resolver; привязка источника не означает, что весь DNS-трафик идёт через этот ISP.

| Среда | Применимость |
| --- | --- |
| Нативный Linux, включая Synology Linux | Привязка исходного IP и строгая policy routing ОС/роутера. Целевая production-среда. |
| Linux Docker host network | Адреса хоста доступны Xray. Рекомендуется для текущего развёртывания. |
| Linux Docker bridge | Доступны только адреса внутри пространства имён. Псевдонимов хоста недостаточно; NAT может стереть различие источников до роутера. Требуется намеренная настройка маршрутизации/SNAT. |
| Нативные Windows и macOS | Работает общая привязка источника TCP/UDP Xray; путь всё ещё определяют наличие локального адреса и маршрутизация ОС/роутера. Не сертифицировано этим набором Linux-тестов. |
| Нативные FreeBSD/OpenBSD | Та же схема привязки в системном dialer с учётом маршрутизации ОС. Нативной приёмки здесь не было. |
| Docker Desktop на Windows/macOS | Сеть Linux VM отличается от хоста; host networking Desktop имеет ограничения привязки конкретного IP. Не считайте LAN-псевдонимы Windows/macOS автоматически доступными контейнеру. |
| WSL2 | Использует сетевое пространство WSL. NAT и mirrored networking требуют отдельной проверки; адреса Windows-хоста не становятся автоматически пригодными источниками. |
| Встроенные ядра Android/iOS | VPN приложения, protected sockets и пользовательские dialer могут менять системное поведение. Общая поддержка не заявлена. |

Реализация рассчитана на обычный системный dialer Xray и поддерживаемые транспорты прокси. Она заменяет привязку источника профиля выбранным оператором путём. Профили с другим dialer, интерфейсом, ненулевой меткой сокета или обходом через другой прокси отклоняются при компиляции нескольких ISP, а не молча обходят выбранный путь. Матрица тестов включает одобренные Xray 26.10.17 и 26.9.30, реальные проверки исходного адреса TCP/UDP на получателе, отказ для неназначенного источника, HTTP/SOCKS TCP/UDP и отключение канала. Другие семейства ядер - точки расширения, а не проверенные реализации нескольких ISP.

`sockopt.mark` - локальная метка сокета Linux; она не передаётся отдельному роутеру MikroTik. `sockopt.interface` и `sendThrough` - разные настройки. Назначение адреса и изменение маршрутов требуют административных прав хоста; использование уже назначенного обычного исходного IP не требует NET_ADMIN у воркера. Сам RelayWeave остаётся Linux-сервисом, поскольку другие компоненты воркера используют Linux API; переносимость Xray не означает переносимость RelayWeave.

## Условия маршрутизации

Зарезервируйте два исходных IP вне DHCP. Для каждого задайте строгий маршрут по источнику через нужный WAN и подходящий обратный NAT. Частный/управляющий трафик должен сохранять локальные маршруты. Проверьте приоритет существующих mangle, VPN-политики, FastTrack, reverse-path filtering, MTU/MSS и формирование трафика каждого WAN. При недоступности выбранного WAN нужен blackhole/маршрут без резервного выхода. Иначе успешный замер может незаметно пройти через неверный ISP. Предпочитайте отдельные объекты маршрутизации изменению всего NAS-трафика или повторному использованию портов источника другого приложения.

Сохраняйте исходные псевдонимы до запуска воркера и поддерживайте динамические WAN-шлюзы. При отключённом WAN его путь приложения тоже должен оставаться отключённым. Включение пути в интерфейсе не включает физический интерфейс. Проверка физического отключения требует отдельного окна обслуживания или изолированной имитации отказа.

## Планирование и наблюдаемость

В политиках auto/throughput веса ISP и профилей общих IP рассчитываются автоматически по качеству, наблюдениям скорости, априорным оценкам ёмкости и активной нагрузке. Явный round-robin сохраняет заданные веса ISP. Необязательная телеметрия роутера только для чтения может уменьшать распределение новых потоков к перегруженному WAN или исключать недавно подтверждённо отключённую линию. При отсутствующих/устаревших данных автономная маршрутизация работает. Семантика, сглаживание и резервный режим описаны в [интеграциях роутеров](router-integrations.ru.md). Псевдонимы подписок не умножают ёмкость общей конечной точки. Это оценки распределения новых соединений, а не равенство байтов или гарантированное измерение свободной полосы Интернета. Верхняя оценка скорости каждого маршрута ограничена бюджетом загрузки его ISP; параметры отдачи описывают бюджет ёмкости, а не ограничитель upload.

Каждый здоровый ISP получает представителя в подготовленном окне кандидатов. Группировка пересекающихся серверных IP сохраняется; варианты разных ISP разделяют идентичность исходного удалённого балансировщика, а не объявляют дополнительную ёмкость сервера. Замеры, circuit breaker и наблюдения передачи относятся к каждому пути. Отключённые пути не компилируются и не проверяются; их существующие сеансы могут завершаться постепенно. Порядок повторов включает другие ISP.

Fallback сохраняет первый здоровый логический профиль и порядок его повторов, но распределяет новые соединения между здоровыми вариантами ISP этого профиля по автоматическим весам каналов. Поэтому закрепление профиля не закрепляет ISP, даже при окне профилей, равном одному. Отключённые и недавно подтверждённо неработающие каналы исключены; существующие соединения сохраняют путь.

Режимы manual/timed/sticky/latency сохраняют прежний порядок. Manual означает первый скомпилированный путь. TCP-соединение или UDP-ассоциация остаётся на одном пути; существующий TCP-сеанс не переносится на другой публичный исходный IP. Это балансировка параллельных потоков, а не объединение одного потока.

Состояние воркера содержит `egress_paths`, `egress` каждого экземпляра, `profile_id`, `route_id`. Маршруты и решения топологии содержат `egress`, раскрытые карточки - ISP и исходный ID профиля. Метод решения `isp_weighted_path_choice` обозначает планирование каналов. Метрика Prometheus `proxy_route_egress_info` связывает ряды маршрутов/экземпляров с ISP/профилем; `proxy_isp_enabled`, `proxy_isp_weight` и `proxy_isp_download_limit_bytes_per_second` показывают настройки канала. Метки описывают намеченную обеспечиваемую политику, а не независимое доказательство захватом пакетов.

## Приёмка и восстановление

Запускайте Go race/vet, настоящие TCP/UDP-тесты одобренных ядер и браузерные тесты на build-01. Наблюдайте реальный внешний исходный IP на получателе/роутере. Публичный выходной IP удалённого прокси не доказывает выбор локального ISP. Сравнивайте параллельную нагрузку одного/двух каналов, только когда оба физических WAN активны; не заявляйте сумму скоростей по loopback-стендам. После выкатки проверяйте HTTP CONNECT, SOCKS TCP, SOCKS UDP и авторизованных потребителей.

Перед выкаткой сохраните зашифрованное состояние приложения, БД и конфигурацию роутера, зафиксируйте контейнеры/образы. Оставьте старые образы доступными. Для отката восстанавливайте настройки приложения, сохраняя исходные псевдонимы и строгие маршруты до завершения старых сеансов. Не очищайте conntrack и не удаляйте маршруты активных сеансов. Откат образа может требовать прежней схемы журнала/конфигурации воркера; используйте защищённую контрольную точку, а не передавайте новые поля путей старому бинарному файлу.
