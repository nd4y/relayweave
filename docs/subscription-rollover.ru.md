# Автоматическая ротация подписок

[English](subscription-rollover.md) | **Русский**

Обычный сценарий - добавить подписки. Автоматический пул обнаруживает пригодные профили; воркер выбирает разнообразные пути прокси/ISP и веса распределения по наблюдаемым задержке, полезному трафику, ограниченным образцам ёмкости, ошибкам и перегрузке. Ручной выбор профилей и весов - расширенные переопределения. Телеметрия роутера необязательна. Автоматические операции не включают отключённый оператором ISP.

## Изменения подписки

Смена только адреса сохраняет все действующие учётные данные, идентичность узла TLS/REALITY, параметры транспорта и неизвестные поля конфигурации. Сопоставление использует типизированный закрытый HMAC-шаблон, а не отображаемые имена или порядок провайдера. Уникальное совпадение сохраняет ID профиля и его исключения. Эквивалентные группы с общими учётными данными могут меняться автоматически, только если ни один участник индивидуально не закреплён, не исключён, не отключён и не переопределён. Другие безопасные независимые группы продолжают обновляться. Если смена адреса/метаданных выводит профиль за явный фильтр хоста/имени/страны, изменение этой группы удерживается, а не неявно отзывает её существующие сеансы. Подтверждённо безопасные группы сохраняют собственную свежесть, а удержанные записи - замороженные сроки.

Изменения учётных данных, ключей, TLS-идентичности, транспорта или неизвестных действующих полей требуют проверки. Прежние принятые пути доступны в пределах своих разрешений. Обычная безопасная смена адреса не требует «Принять». Получение источника по HTTP не разрешает замену конечных точек без участия оператора. Разрешённое исключение привязано к точному ожидающему снимку и версии источника.

Некорректный/пустой/неудачный ответ не стирает каталог и не продлевает его свежесть. Частично разобранный ответ не может молча удалить отсутствующие записи. Безопасные части могут продвигаться, пока удержанные записи сохраняют замороженный срок разрешения. HTTP 304 сохраняет ожидающую проверку и выполняемую ротацию. Пока снимок ожидает проверки, обновление не отправляет условные валидаторы, включая пользовательские условные заголовки, и классифицирует новое тело по текущим правилам. Даже незапрошенный 304 не продлевает удержанное разрешение и не воспроизводит одобрение прежнего выпуска.

## Допуск и непрерывность

Каждое открытие соединения резервирует ссылку на экземпляр ядра до выхода из блокировки допуска. Обычная ротация сохраняет установленные TCP-туннели, half-close и целые SOCKS UDP-ассоциации на исходном экземпляре. Новые назначения внутри существующей UDP-ассоциации сохраняют тот же upstream. Новые ассоциации используют текущую допустимую ревизию. Прямые HTTP-запросы не переиспользуют выводимый из работы upstream для нового запроса.

Новые ревизии прогреваются до ступенчатого перехода 5%, 20%, 50%, 100% новых допусков. Каждая ступень требует прошедшего времени и успешно наблюдаемых сеансов. Низкий трафик не продвигает кандидата только по истечении таймера. На первой ступени ограничены число соединений, частота и байтовые условия допуска. Они останавливают новые допуски, а не прерывают уже принятую длинную передачу.

Обычное исчезновение из полного источника означает вывод из работы с сохранением только установленных сеансов, а не отзыв по безопасности. Отключение, явное исключение политикой, ACL точки входа или смена учётных данных, истёкшее разрешение и отзыв по безопасности приоритетнее продолжения и отката. Неудачный кандидат или старое поколение не могут отменить их. Такие ограничивающие действия могут закрывать существующие TCP/UDP.

Записи ротации, включая старую действующую конфигурацию, хранятся только в аутентифицированном зашифрованном журнале воркера. Повышение доли кандидата ждёт устойчивого сохранения контрольной точки. Ограничивающие изменения применяются до медленного I/O сохранения. После перезапуска воркер проверяет состояние заново, а не восстанавливает устаревшие свидетельства здоровья. Сбой воркера не может сохранить TCP/UDP-сокеты ОС.

## Здоровье и безопасность

TCP-здоровье означает настоящий запрос через прокси, а не открытый локальный SOCKS-порт. UDP проверяется настоящим DNS-запросом/ответом по полному пути отдельно для каждой пары прокси/ISP. Готовность UDP и TCP независима.

Воркер проверяет весь DNS-ответ и закрепляет настоящий серверный сокет Xray за разрешённым числовым IP. Исходные TLS server name и HTTP authority транспорта сохраняются. Замена DNS-конечной точки проходит повторную проверку и ротацию. Локальные адреса, metadata и link-local остаются заблокированы. `allow_private` источника относится только к получению источника. Частный прокси требует явного узкого исключения `proxy_allow_cidrs`; оно не следует из разрешения загружать источник в частной сети. Изменения исключения имеют отдельный барьер допуска.

Артефакты ядер остаются закреплёнными digest. Содержимое подписки не может установить другой исполняемый файл или снять барьеры поколений/допуска/повтора. Старые воркеры не получают назначения, требующие маршрутизации с учётом ревизий; для их старого протокола ограничения допуска проецируются строго.

## Веса и стоимость измерений

Ротация сохраняет иерархический автоматический планировщик: распределение ISP, группа общего серверного IP, затем профиль. Необязательная свежая телеметрия роутера корректирует распределение ISP; её отсутствие сохраняет автономную работу. Псевдонимы с общими удалёнными IP делят оценку ёмкости. Фактические правила весов и свежести описаны в [интеграциях роутеров](router-integrations.ru.md). Полезная переданная скорость - нижняя граница, а не утверждение всей доступной ёмкости. Интерактивная задержка под нагрузкой и суммарная массовая скорость - отдельные цели; один установленный TCP-поток не объединяется через прокси или ISP.

Новые автоматические политики используют дневное резервирование полезной нагрузки замеров 256 MiB. Не более половины доступно автоматическим всплескам измерения скорости; остаток защищает проверки здоровья. Ограниченная цель загрузки по умолчанию - [Cloudflare speedtest download API](https://github.com/cloudflare/speedtest/blob/main/README.md) с ответом 8 MiB. RelayWeave не использует API SDK для выгрузки результатов. Оператор может переопределить цель или задать `disable_speed_probes`. Явные существующие бюджеты сохраняют силу; исчерпание откладывает исследование, а пассивные наблюдения продолжают влиять на выбор. Сетевые кадры/рукопожатия расходуют трафик сверх резервирования полезной нагрузки.

Процент улучшения не обещается. Приёмка сравнивает одинаковую нагрузку с прямым доступом, где применимо, лучшим измеренным отдельным прокси, статическим здоровым набором кандидатов и предыдущим выпуском. Отсутствующая или устаревшая информация роутера не должна мешать базовой работе.

## Ресурсные ограничения и длинные сеансы

Предел процессов остаётся 32, включая завершающие работу и кандидатов; одновременно подготавливаются не более двух экземпляров. Перед созданием процесса проверяется запас памяти/PID cgroup и файловых дескрипторов. Активные, выполняющиеся и измерительные ссылки препятствуют удалению. Артефакты работающих и завершающих работу экземпляров защищены от очистки кэша.

У здоровых разрешённых длинных сеансов нет принудительного максимального возраста по умолчанию. Ограниченное число слотов старых ревизий может задержать следующую ротацию; промежуточные ещё не допущенные наблюдения объединяются. Отключённый воркер консервативно удерживает историю ревизий до замороженного срока. Истечение разрешения или исчезновение настоящего старого сервера не даёт гарантии бесшовного переноса.

## Эксплуатация и проверки

Состояние воркера показывает обезличенные фазы/причины ротации, процент допуска, оставшиеся старые сеансы, готовность протоколов и автоматически рассчитанные веса. `GET /api/v1/sources/{id}/rollovers` фильтрует это представление по источнику. Ожидающая или успешная операция каталога не равнозначна активации воркера или полному завершению старой ревизии.

Только в новой установке добавление источника создаёт автоматический пул, политику и HTTP/SOCKS-точки входа исключительно на loopback. Существующие точки входа оператора не перезаписываются и не расширяются. Выкатка нового бинарного файла остаётся отдельным действием.

Запускайте проверки из изолированной копии на сборочном сервере под общей блокировкой проекта:

```sh
flock -w 50 /home/av/build/relayweave/build.lock bash tools/check-rollover.sh go
XRAY_TEST_ROOT=/path/to/approved/test/core \
  flock -w 50 /home/av/build/relayweave/build.lock bash tools/check-rollover.sh native
flock -w 50 /home/av/build/relayweave/build.lock bash tools/check-rollover.sh database
flock -w 50 /home/av/build/relayweave/build.lock bash tools/check-rollover.sh ui
flock -w 50 /home/av/build/relayweave/build.lock bash tools/check-rollover.sh browser
```

Нативная проверка включает настоящие TCP/UDP Xray, ступенчатую ротацию по реальному времени, устойчивое продвижение допуска и непрерывные старые TCP/UDP-сеансы. Проверка БД создаёт только собственные временные БД/сеть. Браузерные стенды проверяют объяснения автоматических стадий без обычной кнопки «Принять». Unit/race-тесты покрывают семантическое сопоставление, разрешения, конкурентность, вывод из работы, ресурсные бюджеты и ограничивающие изменения. Длительный production-тест, физическая скорость нескольких ISP и production-выкатка - отдельные этапы приёмки, не следующие из этих тестов.
