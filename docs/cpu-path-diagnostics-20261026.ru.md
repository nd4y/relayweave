# Диагностика CPU роутера и путей прокси, 2026-10-26

[English](cpu-path-diagnostics-20261026.md) | **Русский**

Цель 1,5 Гбит/с не достигнута. Выявлены две отдельные проблемы: насыщение CPU
роутера под нагрузкой и периодические зависания на определённом пути
«прокси + ISP2». Позже ISP1 потерял физический Ethernet-линк. Настройки
подключений провайдеров в этих экспериментах не менялись.

## CPU и состояние линка

Менее шумный профилировщик RouterOS, четыре пятисекундных замера
`cpu=all as-value`, показал около 15,62% общей мощности CPU в networking,
15,47% в firewall, 15,09% в queuing и 10,88% в обработке Ethernet. Одно ядро
в среднем было занято примерно на 99%, весь CPU - на 74%. Скорость по полностью
завершённым файлам составила 833,746 Мбит/с, завершились 128/128 объектов.
Это указывает на общее ограничение обработки, но не объясняет исключительно
им каждую медленную передачу. Предыдущий профиль с постоянным выводом в консоль
создавал заметную дополнительную нагрузку.

Роутер зарегистрировал `link down` на ISP1 в **08:06:42 Europe/Moscow**
(сам роутер использует Europe/Samara). Последующие чтения подтвердили `no-link`,
административно включённый интерфейс, остановленный DHCP-клиент и недоступный
маршрут ISP1. Штатный скрипт переключения включил правило выхода через ISP2.
Это произошло до эксперимента RPS, а не вследствие изменения настроек провайдера
в ходе этого эксперимента.

Для A/B/A RPS сохранили свежую исходную конфигурацию и проверили независимый
180-секундный откат на роутере. Временно включали распределение приёма пакетов
между CPU на LAN-транке и двух WAN Ethernet-интерфейсах. Скорость завершённых
файлов составила 713,313 -> 770,284 -> 729,161 Мбит/с; завершилось
123 -> 124 -> 128 объектов из 128. Это не принято как улучшение: ISP1 был
недоступен, а ошибки не позволяют считать выборки доказательством стабильной
пропускной способности. RPS и очереди восстановлены точно; временный таймер
отката удалён. Хеши экспортов настроек провайдеров и маршрутизации совпали с
копией перед RPS. Общий хеш firewall не совпал; чтение правил и логов выявило
штатное переключение относительно более раннего снимка, но полностью не
объяснило расхождение хеша. Firewall не откатывали, чтобы не вмешиваться в
автоматическое переключение каналов.

Общий FastTrack не включали: MikroTik документирует использование только
таблицы main, поэтому обход обработки нельзя без проверки применять к
маршрутизации по источнику. RPS также не гарантирует выгоды на оборудовании
с несколькими RX-очередями. См. [MikroTik Resource](https://help.mikrotik.com/docs/spaces/ROS/pages/40992875/Resource)
и [Packet Flow](https://help.mikrotik.com/docs/spaces/ROS/pages/328227/Packet%2BFlow%2Bin%2BRouterOS).

## Привязка ошибок к путям

PC2 скачивал публичные тестовые объекты с проверкой TLS, без повторных попыток,
с ограничениями параллелизма, времени и объёма. Контрольный Xray копировал
действующие настройки профилей только внутри хоста развёртывания, явно
привязывал исходящий IP и допускал только PC2 и заданные тестовые адреса.

| Тест | Результат |
| --- | --- |
| M1/M2: пять прокси через каждый ISP и два прямых контроля | 144/144 завершились до наблюдавшейся потери линка |
| D1: автоматический RelayWeave, 128 больших объектов, 32 параллельно | 128/128, 608,041 Мбит/с; все передачи сопоставлены с ISP2 |
| D2: та же нагрузка, более поздний автоматический выбор | 123/128, 457,144 Мбит/с; все пять тайм-аутов частичной передачи по 60 секунд на пути P4 + ISP2 |
| M3: пять одинаковых прокси через оба ISP после потери линка | Все 20 передач прокси и четыре прямых контроля ISP1 получили тайм-аут; все 24 передачи ISP2 завершились |
| M4: фиксированный P4 + ISP2 против двух других прокси через ISP2, по восемь больших объектов | P4 завершил 7/8, один тайм-аут частичной передачи на 60 секундах; контрольные пути завершили 16/16 |

В D2 на P4 пришлось 11 передач, пять завершились тайм-аутом; остальные
117 передач теста завершились. M4 воспроизвёл симптом без селектора маршрутов
RelayWeave. Следовательно, в проверенных условиях проблема воспроизводится
на этом пути, но это не устанавливает виновника: удалённый прокси, его канал,
сервер назначения или их взаимодействие. Адреса серверов и реквизиты профилей
здесь не приводятся. Успех на небольших объектах не доказывает устойчивое
качество пути.

## Выпущенное изменение и приёмка

[Необязательная диагностика CONNECT](connect-diagnostics.ru.md) возвращает
выбранные маршрут, профиль и выход только явно разрешённым фактическим
TCP-клиентам. Расшифровка трафика и изменения механизма копирования туннеля
не добавлялись. Заголовки указывают выбранный путь, а не причину тайм-аута.

Воркер собран на build-01: `go test -race ./...`, `go vet ./...`, проверки
CONNECT, аутентификации и подмены заголовков по сети, а также проверки
протоколов и ротации с настоящими Xray 26.10.17 и 26.9.30. Установленный образ:
`sha256:edcb325987be09100c68e2aab3c63304d73c84da4f7e33c9ecc13ef41fd0520b`.
Через Portainer изменены только контейнер воркера и его диагностический список
допуска. Защищённые копии compose/Env и прежний образ сохранены. Миграции
данных не выполнялись.

Проверки с PC2 подтвердили HTTP CONNECT и SOCKS5 TCP с HTTPS 204 и валидным TLS,
а также SOCKS5 UDP DNS. Другой клиент не получил диагностические заголовки даже
с поддельным `X-Forwarded-For`. Оба временных стенда остановлены, процессы
завершены, порты закрыты, закрытые сгенерированные конфигурации удалены.
После потери линка автоматический воркер не имел готовых маршрутов ISP1.

Для следующего сравнения суммарной скорости нужно восстановить физический
линк ISP1. Для нестабильного пути P4 требуется проработка допуска и временного
исключения по устойчивому качеству. Этот диагностический выпуск не вводит
новую политику карантина; краткую успешную проверку нельзя считать устранением
его зависаний при передаче данных.
